## 4. 核心控制思路

### 4.1 为什么要分 prefill 和 decode

LLM 推理可以分为两个阶段：

| 阶段 | 特点 | 功率控制关注点 |
|---|---|---|
| Prefill | 处理输入 prompt，主要影响 TTFT | 输入 token 数越多，TTFT 与能耗越高；需要限制 TTFT 增加 |
| Decode | 逐 token 生成输出，主要影响 TBT 和 E2E | 输出越长，decode 时间越长；功率控制收益更明显 |

静态功率封顶实验说明，单一 power cap 能节能，但无法针对阶段差异优化。低功率如 150W 虽然可节能约 24%，但 E2E 增加约 15%-17%，代价偏大。因此后续采用分阶段控制。

### 4.2 Prefill 策略

Prefill 阶段使用输入规模或 query count 选择功率：

```text
q <= 16        -> 200W
32 <= q <= 64 -> 220W
q >= 103      -> 260W
```

对比策略：

- `baseline_350w`：全程 350W。
- `Token fit`：根据 token-power 拟合曲线给出功率。
- `200/220/260W`：人工分段桶，更简单稳定。

结论：`200/220/260W` 在 prefill-only 策略评估中 GEOMEAN 节能 8.75%，TTFT 增加 2.70%，比 Token fit 的 3.85% 节能更适合作为最终 prefill 前馈策略。

### 4.3 Decode 策略

Decode 阶段先做 power cap sweep，再选择满足 TBT 约束的功率桶。最终用于主实验的 guarded decode 桶为：

```text
q = 8, 16, 32 -> 190W
q = 64, 96    -> 205W
q = 128       -> 210W
```

解码阶段候选策略包括：

| 策略 | 功率映射 | 特点 |
|---|---|---|
| `scheme1_fit_curve` | 8->150W, 16->151W, 32->191W, 64->210W, 96/128->220W | 最激进，节能最高，但短输出延迟代价大 |
| `scheme2_fit_plus` | 8->150W, 16->170W, 32->200W, 64->220W, 96/128->230W | 比 scheme1 保守，但长输出节能接近消失 |
| `scheme3_kv_guided` | 8/16/32->190W, 64/96->205W, 128->210W | 最均衡，主文推荐 |

### 4.4 前馈控制器

前馈控制的运行逻辑：

1. 请求开始前，根据总输入 token 或 query group 设置 prefill power cap。
2. 首 token 到达后进入 decode 阶段。
3. 运行时根据当前生成 token、未完成请求和 KV pressure 估计负载。
4. 按 decode 推荐表或功率桶切换 power cap。
5. 每个 batch 记录 power event trace、平均功率、能耗、TTFT、TBT、E2E。

关键代码位置：

```text
run_feedforward_evaluation.py
  FeedforwardController
  FeedforwardController.start()
  FeedforwardController.handle_stream_event()
  compute_kvb()
  get_recommended_decode_power()
  build_power_window_stats()
```

可讲解的代码流程：

```text
LoadGenerator 选 prompt
  -> LLMInferencer 发请求并流式返回事件
  -> FeedforwardController 监听 first_token/chunk/finished
  -> power_control.set_power_cap 下发 power cap
  -> PowerMonitor 采样功率
  -> raw CSV 写 batch 级数据
  -> aggregated CSV 写 full-repeat 聚合数据
```

### 4.5 PID guard 控制器

PID guard 不是替代前馈，而是叠加在前馈功率桶上的保护机制：

```text
power = feedforward_base_power + pid_delta
```

它只做正向补偿，即延迟超预算时加功率，延迟低于预算时不会在前馈功率基础上继续主动降功率。

当前关键参数：

| 参数 | 值 | 含义 |
|---|---:|---|
| `kp_prefill` | 0.1 | TTFT 误差比例增益 |
| `kp_decode` | 0.45 | TBT 误差比例增益 |
| `ki` | 0.0 | 当前主实验中积分项关闭 |
| `kd` | 0.0 | 当前主实验中微分项关闭 |
| `pid_interval_sec` | 2.0 | Decode PID 更新间隔 |
| `pid_delta_limit_w` | 20.0W | 最大补偿量 |
| `pid_max_step_w` | 10.0W | 单次最大功率步长 |
| `pid_min_power_change_w` | 5.0W | 小变化不下发 |
| `pid_deadband_ms` | 1.0ms | TBT 死区 |
| `pid_tbt_budget_ratio` | 1.05 | TBT 目标倍率 |
| `pid_ttft_budget_ratio` | 1.05 | TTFT 目标倍率 |

公式：

```text
TTFT target = TTFT_ff * 1.05
TBT target  = TBT_ff  * 1.05

prefill_delta_w = clamp(0.1  * TTFT_error_ms, 0, 20)
decode_delta_w  = clamp(0.45 * TBT_error_ms,  0, 20)
```

关键代码位置：

```text
run_feedforward_evaluation.py
  FeedforwardPIDGuardController
  PIDState
  get_pid_targets_for_query()
  load_pid_targets()
  pid_event_trace_json / power_event_trace_json
```

运行时 PID 事件也会写入 CSV 字段，因此可以从聚合结果和 raw 结果中追溯 PID 更新次数、补偿功率和反馈 TBT。

关键输出字段：

```text
pid_enabled
pid_update_count
pid_prefill_delta_w
pid_decode_delta_w
pid_prefill_error_ms
pid_decode_error_ms
pid_decode_feedback_tbt_ms
pid_event_trace_json
```

结题讲解重点：PID guard 的目标不是让延迟回到 350W baseline，而是在前馈节能的基础上避免明显超过预算，提升稳定性。

## 8. 结题讲解顺序建议

### 8.1 开场：问题定义

可以这样讲：

```text
大语言模型推理默认使用较高 GPU 功率上限，但实际推理阶段中功率需求并不恒定。目标是在尽量控制 TTFT、TBT 和 E2E 延迟代价的前提下，通过动态 power cap 降低 GPU 推理能耗。
```

展示：

- `实验参数表格.md`
- `start_vllm_server.sh`
- `/v1/models` 返回结果

### 8.2 第一部分：静态实验说明节能空间

展示：

- `静态功率封顶实验.md`
- `experiment_results/legacy/results0/img_bigger/` 或 `img/` 中的静态功率图

讲解重点：

- 150W 能省约 24%，但延迟增加 15%-17%。
- 200W 能省约 10%-11%，延迟增加约 3%-4%。
- 静态功率不能适配不同阶段，因此进入分阶段建模。

- Decode 主要关注 TBT 和 E2E。
- Decode 功率随 KV/output 增长后进入饱和区，支持使用功率桶。

### 8.4 第三部分：策略评估

展示：

## 9. 答辩时可直接引用的关键结论

1. 静态功率封顶证明 GPU 推理有明显节能空间，但低功率会带来不可忽略的延迟代价。
2. Prefill 和 Decode 的功率-延迟特性不同，因此采用分阶段建模和分阶段控制。
3. Prefill 阶段推荐 `200/220/260W` 分段桶，GEOMEAN 节能 8.75%，TTFT 增加 2.70%。
4. Decode 阶段推荐 `scheme3_kv_guided`，GEOMEAN 节能 9.62%，TBT 增加 3.18%。
5. 完整纯前馈控制在 Qwen out100/out200 下分别取得 10.64% 和 11.89% GEOMEAN 节能。
6. 前馈+PID 在 Qwen out100/out200 下分别取得 10.34% 和 11.43% GEOMEAN 节能，同时将 TBT/E2E 代价维持在约 4%。
7. Llama 8B AWQ-INT4 迁移实验取得 13.29% GEOMEAN 节能，TBT/E2E 增加约 5%，证明方法具备一定可迁移性。
8. 当前系统不仅有算法结果，还有可复现实验脚本、raw/aggregated 数据、metadata、progress 文件、论文图和测试脚本。

## 11. 代码详细讲解

这一部分专门用于结题检查时讲代码实现。建议展示时打开 `run_feedforward_evaluation.py` 作为主线文件，再按调用链跳到 `llm_inference.py`、`power_control.py`、`monitor.py` 和绘图脚本。

### 11.1 代码整体分层

代码可以按五层讲：

| 层次 | 代表文件 | 作用 |
|---|---|---|
| 服务层 | `start_vllm_server.sh` | 启动 vLLM OpenAI 兼容 API，加载本地模型 |
| 请求层 | `llm_inference.py`、`load_generator.py` | 构造真实请求，发送到 vLLM，记录请求级延迟 |
| 控制层 | `power_control.py`、`run_feedforward_evaluation.py` | 根据策略设置 GPU power cap，并在流式生成过程中动态调整 |
| 监测层 | `monitor.py` | 采样功率、clock、显存，计算平均功率和能耗 |
| 分析展示层 | `analyze_*.py`、`plot_*.py` | 生成 aggregated CSV、Markdown 报告和论文图 |

讲解时可以强调：实验不是离线模拟，控制层会真实调用 `nvidia-smi -pl` 修改 GPU power cap，监测层同步采样真实功率曲线，再用实验数据计算能耗和延迟。

### 11.2 服务启动代码：`start_vllm_server.sh`

该脚本负责把模型服务启动成 OpenAI 兼容 API。当前核心配置是：

```bash
MODEL_PATH="./Meta-Llama-3.1-8B-Instruct-AWQ-INT4"
MODEL_NAME="Meta-Llama-3.1-8B-Instruct-AWQ-INT4"
GPU_MEM_UTIL="0.85"
MAX_MODEL_LEN="32768"
MAX_NUM_BATCHED_TOKENS="2048"
MAX_NUM_SEQS="64"
```

启动命令核心部分：

```bash
python -m vllm.entrypoints.openai.api_server \
  --model "$MODEL_PATH" \
  --served-model-name "$MODEL_NAME" \
  --quantization awq \
  --gpu-memory-utilization "$GPU_MEM_UTIL" \
  --max-model-len "$MAX_MODEL_LEN" \
  --enable-chunked-prefill \
  --max-num-batched-tokens "$MAX_NUM_BATCHED_TOKENS" \
  --max-num-seqs "$MAX_NUM_SEQS" \
  --no-enable-prefix-caching
```

这里需要解释两个关键点：

- `--max-model-len 32768`：Llama 3.1 默认上下文为 131072，单卡 16GB 显存下 KV cache 不够，所以显式收紧最大上下文长度。
- `--no-enable-prefix-caching`：关闭 prefix cache，避免缓存影响 TTFT、能耗和策略对比公平性。

结题展示可以先运行：

```bash
curl -sS http://localhost:8000/v1/models
```

它能证明服务层可用，并且当前加载的是 Llama 8B AWQ-INT4。

### 11.3 负载生成代码：`load_generator.py`

`load_generator.py` 主要有两个类：

| 类 | 作用 |
|---|---|
| `ShareGPTLoader` | 读取 ShareGPT 数据，提取用户 prompt |
| `LoadGenerator` | 根据目标 token 数、query count 和实验类型生成请求列表 |

关键函数：

```text
LoadGenerator.generate_load()
LoadGenerator.generate_prompt_by_token_count()
```

在主实验中，负载不是随便构造固定字符串，而是从 ShareGPT 中按目标输入 token 数选 prompt。这样做的意义是：

- 输入长度更接近真实用户请求。
- 不同 query count 下有不同输入 token 规模。
- 每个实验可以通过 `queue_seed` 和 `sampling_seed` 固定随机性，保证复现。

主实验使用的 query group 在 `run_feedforward_evaluation.py` 里定义：

```python
QUERY_GROUPS = [
    {"query_count": 8, "target_input_tokens": 225},
    {"query_count": 16, "target_input_tokens": 504},
    {"query_count": 32, "target_input_tokens": 1581},
    {"query_count": 64, "target_input_tokens": 2175},
    {"query_count": 96, "target_input_tokens": 11106},
    {"query_count": 128, "target_input_tokens": 22873},
]
```

结题时可以讲：query count 控制并发请求数量，target input tokens 控制 prefill 工作量，output length 控制 decode 工作量。

### 11.4 请求执行代码：`llm_inference.py`

`llm_inference.py` 中的核心类是：

```text
LLMInferencer
```

它负责调用 vLLM OpenAI 兼容接口，并把每个请求的时间信息记录下来。实验需要的三个主要延迟指标是：

| 指标 | 含义 | 代码记录方式 |
|---|---|---|
| TTFT | Time To First Token，首 token 延迟 | 请求开始到第一个 token 到达 |
| TBT | Time Between Tokens，token 间隔 | decode 阶段相邻 token 的平均时间 |
| E2E | End-to-End latency | 请求开始到请求完成 |

该文件的价值在于：它把模型调用封装成统一接口，后面的 prefill、decode、前馈、PID 实验都复用同一套请求路径。这样不同策略之间的差异主要来自 power cap，而不是请求实现差异。

在前馈+PID实验中，`LLMInferencer` 还会配合流式事件，把 `first_token`、`chunk`、`finished` 等事件交给控制器。控制器根据这些事件判断当前处于 prefill 还是 decode，并决定是否切换功率。

### 11.5 功率控制代码：`power_control.py`

`power_control.py` 是硬件控制封装。结题时重点展示这几个函数：

```text
get_power_cap(device_index=0)
set_power_cap(watts, device_index=0, sudo_password=None)
get_current_power(device_index=0)
get_gpu_name(device_index=0)
SudoKeepAlive
```

其中 `set_power_cap()` 的职责是把策略给出的功率值下发到 GPU：

```text
策略计算出 power_w
  -> set_power_cap(power_w)
  -> sudo nvidia-smi -i <gpu> -pl <power_w>
  -> 可选读取 actual power limit 验证
```

这里要说明两个工程细节：

- 实验要频繁切换 power cap，所以封装了 `SudoKeepAlive`，避免长实验中 sudo 过期导致失败。
- `validate_actual_power_limit()` 会检查实际功率上限是否接近期望值，避免命令失败但实验继续跑。

可以讲的关键点：功率控制是通过 NVIDIA 官方工具 `nvidia-smi` 实际修改硬件 power limit，不是只在软件里记录一个策略标签。

### 11.6 功率监测代码：`monitor.py`

`monitor.py` 的核心类是：

```text
PowerMonitor
```

运行逻辑：

```text
PowerMonitor.start()
  -> 后台线程周期采样 GPU
  -> 记录 timestamp、power_w、clock、memory 等
PowerMonitor.stop()
  -> 返回完整采样序列
```

在实验脚本中，`build_power_window_stats()` 会从采样点中截取当前 batch 的时间窗口，并计算：

```text
avg_power_w
total_energy_j
peak_power_w
avg_sm_clock_mhz
avg_mem_clock_mhz
```

能耗计算口径：

```text
total_energy_j = avg_power_w * duration
```

对于结题讲解，可以强调：能耗不是根据 power cap 估计，而是根据实际采样功率计算。power cap 是上限，实际功耗会随负载变化。

### 11.8 实验块调度：如何保证对比公平

主实验不是简单先跑完一个策略再跑另一个策略，而是构造 experiment blocks：

```text
build_experiment_blocks()
```

一个 block 通常包含：

```text
strategy
query_count
output_length
full_repeat
batch_repeat
```

实验运行时会按 block 遍历，每个 block 内执行若干 batch。这样可以保证：

- 每个策略覆盖同样的 query group。
- 每个策略覆盖同样的 output length。
- 每个配置有相同 `repeats_per_batch` 和 `full_repeats`。
- warmup batch 不计入最终统计，降低冷启动影响。

输出文件包括：

```text
*_raw.csv
*_aggregated.csv
*_metadata.json
*_progress.json
```

这里可以讲：raw CSV 保留每个 batch 的原始观测，aggregated CSV 用于论文表格和图，metadata 记录实验参数，progress 便于长实验中断后检查进度。

### 11.9 纯前馈控制器：`FeedforwardController`

纯前馈控制器代码位置：

```text
run_feedforward_evaluation.py
  class FeedforwardController
  start()
  handle_stream_event()
```

运行逻辑可以分成两步：

第一步，prefill 前设置功率：

```text
controller.start()
  -> 如果是 baseline，设置 350W
  -> 如果是 feedforward，按输入 token / prefill bucket 设置 prefill power
```

第二步，decode 中根据流式事件更新功率：

```text
handle_stream_event(event)
  -> 更新每个请求已生成 token 数
  -> 判断请求是否 finished
  -> 计算当前 KVB / decode pressure
  -> 查 decode_buckets 或 recommendation json
  -> 如果目标功率变化，则调用 set_power_cap()
```

控制器记录的 trace：

```text
power_event_trace = [
  {
    "power_limit": ...,
    "reason": "prefill" 或 "decode",
    "wall_time": ...,
    "kvb": ...
  }
]
```

这部分可以作为现场代码重点：它说明系统不是固定跑一个功率，而是在请求生成过程中根据运行状态动态调整功率。

### 11.10 PID 控制器：`FeedforwardPIDGuardController`

PID guard 控制器代码位置：

```text
run_feedforward_evaluation.py
  class PIDState
  class FeedforwardPIDGuardController
```

它与纯前馈的区别是：先得到前馈基础功率，再根据 TTFT/TBT 反馈做正向补偿。

核心结构：

```text
prefill_base_power_limit
prefill_power_limit
current_decode_base_power
pid_prefill_delta_w
pid_decode_delta_w
pid_event_trace
```

prefill 阶段：

```text
base_power = get_prefill_power_for_total_tokens(...)
desired_power = base_power + pid_prefill_delta_w
_apply_power(desired_power, reason="prefill")
```

decode 阶段：

```text
根据流式 token 事件估计当前 feedback_tbt_ms
与 target_tbt_ms 比较
如果连续超过预算窗口，则计算 decode_delta_w
desired_power = decode_base_power + decode_delta_w
按 pid_max_step_w 限制单次调节幅度
调用 set_power_cap()
```

PID 的实际公式在 `PIDState` 中：

```text
error = actual_value - target_value
integral = integral + error
derivative = error - prev_error
raw_delta = kp * error + ki * integral + kd * derivative
delta_w = clamp(raw_delta, 0, pid_delta_limit_w)
```

当前主实验中 `ki=0`、`kd=0`，所以主要是比例补偿：

```text
decode_delta_w = clamp(0.45 * TBT_error_ms, 0, 20)
```

为什么只允许正向补偿：

- 前馈策略本身已经是节能策略。
- PID guard 的目标是防止延迟超预算，不是进一步压低功率。
- 如果允许负向补偿，可能导致节能更高但延迟不稳定，难以解释。

这部分可以作为答辩亮点：系统结合了前馈和反馈。前馈负责快速给出合适功率，反馈负责处理运行时偏差。

### 11.11 Prefill 策略代码：`run_prefill_concurrent_evaluation.py`

prefill-only 实验用于隔离 prefill 阶段，因此输出长度固定为 1 token。核心函数：

```text
evaluate_prefill_token_power_fit(total_input_tokens)
recommend_prefill_power(strategy, ...)
run_prefill_concurrent_evaluation(...)
```

策略定义：

```text
baseline_350w
prefill_token_fit
prefill_token_fit_plus25w
prefill_manual_buckets
```

代码逻辑：

```text
选择 query group
  -> 从 ShareGPT 选 prompt
  -> 根据策略推荐 prefill power
  -> 设置 power cap
  -> 发送 max_tokens=1 的请求
  -> 采集 TTFT 和能耗
  -> 输出 raw/aggregated CSV
```

为什么 `max_tokens=1`：这样完整请求主要由 prefill 决定，decode 只生成一个 token，可以更清楚地评估 prefill 功率策略对 TTFT 和能耗的影响。

### 11.12 Decode 策略代码：`run_decode_strategy_evaluation.py`

decode-only 策略评估使用固定 1 token prompt，控制输入侧开销，重点观察不同输出长度下的 decode 行为。

核心函数：

```text
get_power_for_decode_strategy(strategy, ...)
run_decode_strategy_evaluation(...)
aggregate_results(...)
```

策略定义：

```text

```

运行逻辑：

```text
构造短 prompt
  -> 设置目标 output_length
  -> 设置对应策略 power cap
  -> ignore_eos=True 保证固定输出长度
  -> 采集 TBT、TTFT、E2E、energy
  -> 相对 baseline 计算 energy saving 和 tbt loss
```

这个脚本支撑了后续 guarded decode power buckets 的选择，是从建模到完整控制的中间验证环节。

### 11.13 分析脚本：`analyze_*.py`

分析脚本的共同模式：

```text
load_latest_aggregated_csv()
  -> compute_relative_plot_df()
  -> plot_metric()
  -> plot_relative_metric()
  -> write report.md
```

主要分析脚本：

| 文件 | 输入 | 输出 |
|---|---|---|
| `analyze_feedforward_evaluation.py` | 前馈 aggregated CSV | energy、power、TTFT、TBT、E2E、relative 图 |
| `analyze_prefill_concurrent_evaluation.py` | prefill raw/aggregated CSV | prefill 策略图、fit 图、异常过滤数据 |
| `analyze_decode_strategy_evaluation.py` | decode q8/q16 aggregated CSV | decode 策略对比图和报告 |

统一计算公式：

```text
Energy Saving = (1 - strategy_energy / baseline_energy) * 100
Latency Increase = (strategy_latency / baseline_latency - 1) * 100
```

讲解时强调：相对指标只和同一实验目录内的 `baseline_350w` 对比，不跨实验目录混用 baseline，避免环境波动污染结果。
